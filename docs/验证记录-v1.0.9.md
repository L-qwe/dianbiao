## 源码核对与修复

1. APP 的 `ApProvisioner` 访问 `/api/device-info`，原 DianBiao 未注册该路由，落入 API 404。现热点和 STA 地址均提供此接口，响应为 UTF-8 JSON，禁用缓存。
2. APP 的 `DeviceInfo` 使用 `wifi_status` 判断在线状态，并读取 `wifi_port`。原公共 JSON 缺少这两个字段，APP 会使用 `unknown` 和 80 的默认值。现 HTTP 与 BLE a04 共用实时公共字段，包括真实端口、当前 SSID、IP 和 Wi-Fi 状态。HTTP 额外保留 12 路运行数据。
3. APP `BleProvisioner` 使用 `WRITE_TYPE_NO_RESPONSE` 写 a02，原固件只声明 `WRITE`。现同时声明 `WRITE | WRITE_NR`，UUID 与参考项目一致。仍接受 `SSID|PASSWORD` 和旧逗号分隔形式；不再裁剪有效凭证中的空格。
4. 参考项目有独立的平台登记任务，DianBiao 原来没有。现联网/重连后向 `http://10.0.100.65:8080/anton/device-access/report` 发出登记，成功每 60 秒刷新，失败每 15 秒重试。任务创建失败也有重试间隔。主循环生成报文快照，HTTP 在后台执行，连接/读取超时分别为 3/5 秒；不读取响应体。包含 MAC、固件版本/类型、STA IP、HTTP 端口、联网状态，不伪造验针机的电源或 SD 字段。
5. 公共 JSON 转义补齐控制字符，SSID 中的引号、反斜杠和控制字符不会破坏 JSON。

保持电表类型 `DianBiao 电表脉冲采集`、脉冲采集/计量逻辑、NVS 命名空间、BLE UUID 和现有 MQTT 协议。

## APP 扫描前缀

APP 添加页根据“设备类型管理”里的标识及分类前缀筛选 Wi-Fi 和蓝牙名称。源码默认只初始化验针机 `YanZhenJi_` 和安东 `Andon_`；用户自建类型保存在手机中，不能仅凭 APP 源码确认当前手机是否已有电表类型。

本版保留电表身份：

- BLE：`DianBiao_<12位Wi-Fi MAC，无冒号>`。
- 默认热点：`DianBiao_<MAC后6位>`；已有自定义热点名保留。
- APP 若尚未配置，在现有“设备类型管理”中添加名称“电表”、标识 `DianBiao_`，无需修改/重新编译 APP。
- 已自定义热点名称时，热点名前缀也要匹配现有设备类型标识。

## 升级与现场验收

已有相同分区的 N16R8 使用 `dist/DianBiao_v1.0.9_16MB_ota.bin`；首次串口烧录使用 factory 镜像，地址 `0x0`。

1. 升级后确认版本为 v1.0.9，APP 电表类型标识为 `DianBiao_`。
2. 热点添加：连接设备热点，在 PowerShell 中执行 `Invoke-RestMethod 'http://192.168.4.1/api/device-info'`，应返回 MAC/固件信息；再使用 APP 热点方式添加。APP 目前的热点方式读取设备信息，路由器凭证通过设备网页配置。
3. 蓝牙添加：扫描 `DianBiao_` 开头设备，读取 MAC 后配置 2.4GHz Wi-Fi；核对 `CONNECTED,<IP>` 结果及 APP 地址。
4. 设备联网后观察串口 `[DEVICE-ACCESS] report OK, HTTP ...`。若失败，记录状态码并检查到上述内网平台的连通性及服务端类型支持。
5. 比较热点/STA HTTP 与蓝牙返回的 MAC，核对保存后设备状态和 12 路计数持续采集。
